# Draft KCOM claim reference tooling

This module provides offline eligibility, selection review, settlement arithmetic and activation previews. It builds no transactions and proves no on-chain authorization, claim acceptance or campaign settlement. The strict claim expiry gate remains failed. The format is a draft, not an approved covenant ABI.

## Import existing normalization output

`importKcomClaimMaterialization` consumes the existing backend-v2 `SealedMaterialization`, an independently supplied expected content hash, campaign/token IDs, provenance commitments and a destination-address-to-script adapter.

It recomputes the backend's canonical SHA256, verifies frozen 86/10/4 contributions against raw micro-point bucket totals, reconciles destination totals and combines exact shares for aliases of the same decoded authority before rounding. It preserves existing points/export semantics. An empty positively weighted source bucket is rejected pending an explicit campaign policy; it is never silently reassigned.

The adapter accepts standard native Schnorr, ECDSA and P2SH destination scripts. All five KCC20 authority schemes are supported by the explicit authority manifest and chosen-beneficiary types. Beneficiary authorization is still a contract responsibility. Provenance hashes bind the chosen source exports, cutoff, membership and integrity manifest; they do not themselves re-audit those datasets or establish that the external expected hash was approved.

The genuine synthetic fixture in `test/fixtures/kcom-backend-materialization.json` was generated by the existing backend-v2 allocation, eligibility and materialization services at reviewed revision `c5eca218`. It includes an excluded wallet and an unlinked EVM wallet that are retained in the audit but absent from eligible allocations. Its sources are synthetic and its destination addresses are public TN10 proof wallets. It is not production allocation data.

## Eligibility encoding

`buildKcomClaimManifest` canonicalizes and aggregates original authorities, sorts by scheme/identifier, validates positive signed-64-compatible raw allocations and emits a public manifest. Source materialization shares are converted to raw units only once. Any base floor residual is reserved for treasury, separately from unclaimed base that benefits Long participants.

Draft leaf encoding is BLAKE3 over domain `kcom.claim.eligibility.leaf/v1\0`, campaign ID (32 bytes), index (u32 little endian), scheme (u8), authority (32 bytes) and base entitlement (u64 little endian). Tree width is the next power of two. Padding uses its own domain and index; internal nodes use an ordered, distinct node domain. Maximum depth is 20. Canonical JSON manifest content uses SHA256. Root and leaf count must both be authenticated externally before relying on a proof.

`createKcomClaimProof` exports one path. `createKcomClaimProofs` hashes/validates the tree once and produces all paths without rebuilding it per wallet. `verifyKcomClaimProof` requires the expected campaign, root and leaf count. `verifyKcomClaimManifest` requires an external expected content hash.

Nullifiers bind campaign plus original authority, independent of chosen tier or redirected destination. Selection digests also commit root, nullifier, tier and chosen beneficiary. A digest or valid membership proof is not a wallet signature and does not mark a claim used.

## Settlement and activation

`settleKcomClaimReference` consumes explicit selection fixtures, rejects duplicate original identities and applies the cumulative pools. It separately floors Medium, Long and unclaimed-base shares. Zero qualifying denominators return corresponding funds to treasury. Output order is canonical and independent of input order. Treasury breakdown reconciles base rounding, boost residuals and unclaimed-base residuals, while liabilities remain the full accepted-selection allocations.

The reference has no chain evidence or recovery authority. `treasuryRaw` is a calculation, not authorization to withdraw. No accepted unactivated rights expire.

`reviewKcomClaimActivation` recomputes allocation and returns the exact existing KCOMVesting state with full allocation, released=0, chosen beneficiary and supplied frozen TGE. It returns zero direct activation-time payout; TGE is released afterward. Tests validate and encode the preview using the real pinned vesting ABI. Claim/settlement/vault provenance and atomic activation still require campaign contracts.

## Checks

```sh
npm run test:kcom-claim-policy
npm test
```

The suite includes 1/3/5-leaf independent Python BLAKE3/SHA256 vectors and 64 independent Python unequal-weight settlement vectors, every absent/Short/Medium/Long combination for three identities. The Python generator is `scripts/generate-kcom-policy-vectors.py`; it uses Python's `blake3` package and never calls the TypeScript module.

The 1,000-equal-wallet case uses 100 Short, 200 Medium, 300 Long and 400 unclaimed. At eight decimals Short receives 2M, Medium 16M, Long 81,999,999.999996 KCOM, and treasury receives 400 raw units (0.000004 KCOM) from independently floored shares. Together they total exactly 100M.

ESM/CommonJS exports agree. Tests also cover aliases, tampered shares/hashes/proofs, wrong campaigns, unsupported schemes, canonical integer limits, redirected identities, duplicate selections and full-allocation activation accounting. No funded campaign or application deployment is established by these checks.

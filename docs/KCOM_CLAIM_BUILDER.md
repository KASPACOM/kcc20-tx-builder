# KCOM campaign transaction builder status

The TN10-only `kcom-claim.fund-vault`, `kcom-claim.create-shard`, `kcom-claim.finish-initialization`, `kcom-claim.collect`, `kcom-claim.finish-settlement`, `kcom-claim.seal` and `kcom-claim.activate` operations use the campaign artifacts pinned from [contract PR #499](https://github.com/KASPACOM/kaspa-covenants/pull/499). Each builds an unsigned PSKT. The wallet signs only the native fee input: index 2 for vault funding, shard collection and sealing, index 1 for factory and settlement-finish steps and index 3 for activation. The graph-owned KCC20 reserve uses canonical owner-scheme-4 authorization by the vault input.

Funding requires two separate transactions. First, the existing canonical `kcc20.transfer` operation sends the exact campaign budget to the derived campaign graph covenant ID with owner scheme 4. After that accepted token output is live, `kcom-claim.fund-vault` spends it together with the still-unfunded vault output. The builder reconstructs the vault successor and unchanged canonical token reserve, checks both current source outpoints and their covenant IDs, and returns a rebuild-required error for stale sources. It pays the fee from a separate wallet UTXO. A submitted PSKT is not accepted funding until chain and indexer evidence confirm the spend.

The build request uses the existing `kcc20-in-process-pskt-builder-input/v1` envelope with `builderKey: "kcom-claim.fund-vault"`, `network: "testnet-10"`, a TN10 `owner.walletAddress`, and these `params`:

| Field | Meaning |
| --- | --- |
| `graphId` | Derived campaign graph covenant ID, 32-byte hex |
| `vaultState` | Exact current `KCOMVault` state, including frozen terms and `funded: false` |
| `vault` | Current vault `{ transactionId, index }` outpoint |
| `tokenState` | Exact graph-owned canonical KCC20 source state |
| `token` | Current token `{ transactionId, index }` outpoint |

After the campaign factory is opened, `kcom-claim.create-shard` spends its current factory outpoint and creates one numbered shard. Its request uses the same envelope with `builderKey: "kcom-claim.create-shard"` and `params: { graphId, factoryState, factory }`. `factoryState` is the exact open `KCOMFactory` state; `factory` is its current `{ transactionId, index }` outpoint. The builder derives the next factory state and initial shard state from that source, preserves their combined native KAS, and rejects a stale factory or a completed shard sequence. Each accepted shard creation consumes the previous factory, so the next build needs the new outpoint and incremented state. Once every shard exists, `kcom-claim.finish-initialization` takes the same request fields and replaces the final factory with the initial settlement collector. The collector inherits the factory's native KAS and starts with empty participation totals.

After manual close, `kcom-claim.collect` takes `params: { graphId, collectorState, closedShardState, depth, unusedProof, collector, closedShard }`. It verifies the next numbered closed shard, an empty summary slot and matching campaign terms, then replaces both inputs with one collector carrying their native KAS and combined participation. `unusedProof` is the hex Merkle proof for the empty summary slot, and `depth` must match the power-of-two shard count. After the collector has processed every shard and entitlement, `kcom-claim.finish-settlement` takes `params: { graphId, collectorState, collector }`. It requires complete shard coverage, exact settlement count and a liability within the budget. It preserves the collector's native KAS while marking the state complete. Then `kcom-claim.seal` takes `params: { graphId, vaultState, collectorState, vault, collector }`. It verifies that the funded vault remains unsettled and that the collector is complete. It spends both graph actors, preserves their combined native KAS in one settled vault output, and freezes the exact liability carried by the collector. The sponsor pays each fee. None of these steps consumes a token reserve.

After settlement, `kcom-claim.activate` takes `params: { graphId, vaultState, entitlementState, tokenState, vault, entitlement, token }`. States must match their live source UTXOs and the frozen campaign identity. The operation spends the vault, one immutable entitlement and its exact canonical token reserve, derives a new beneficiary-bound vesting position from vault input 0 and position output 1, and transfers the **full** entitlement into that position's reserve. It automatically chooses partial activation when a vault reserve remains and final activation when this is the last liability. The sponsor pays the fee and any native KAS needed to split the token reserve. Activation pays no TGE tokens; the separate vesting release operation handles that. A stale or competing source requires rebuilding with the new accepted outpoints.

The local pinned-WASM test checks artifact pins, source and successor scripts, amounts, signing indexes, stale-source rejection and fee-output mutation. Vault funding's scripts, all four shard-creation successor scripts, the initial collector and sealed vault scripts, and the first partial/final activation scripts and position IDs match the synthetic Argent-engine `tn10-proof-mixed` receipt in [#499](https://github.com/KASPACOM/kaspa-covenants/pull/499). The builder commits budgets 60/20 for vault/token inputs, above measured 52/15; 30 for shard creation, above measured 22; 40 for initialization finish, above measured 29; 45/30 for collection, above measured 31/23; 40/25 for sealing, above measured 28/15; and 100/35 or 70/25 for activation vault/token inputs, above measured 79/25 or 56/15. Fee inputs commit 10. Local signed wire tests in #499 execute the available campaign PSKTs in Argent against synthetic sources; none establishes TN10 acceptance. Backend accepted-deployment verification, token-profile transfer compatibility and funded multi-wallet proof remain required before using real campaign funds. Opening, tier selection, close, per-claim settlement and recovery builders remain unfinished.

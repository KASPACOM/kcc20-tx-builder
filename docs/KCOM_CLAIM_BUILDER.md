# KCOM campaign transaction builder status

Campaign creation starts with `kcom-claim.deploy-initializer`. It requires the exact frozen 277-byte terms, reviewed eligibility manifest and trusted content hash, initializer state, and enough native KAS for the configured shard cells plus the vault cell. The sponsor signs its native input. After that deployment is accepted, `kcom-claim.initialize` spends the live initializer and creates the factory and vault under one derived graph covenant ID. Two frozen administrators sign the prepared initializer input, then the sponsor signs its fee input. Both calls return the existing PSKT envelope; an initializer output is not accepted merely because the deployment was built or submitted. The builder checks the linked actor-template witnesses from the pinned Argent graph artifact. The linked template hash differs from the ordinary SIL actor template hash even though the resulting factory and vault scripts are identical. Mixing those witness forms makes the initializer fail in the real engine.

The TN10-only `kcom-claim.fund-vault`, `kcom-claim.open`, `kcom-claim.create-shard`, `kcom-claim.finish-initialization`, `kcom-claim.select`, `kcom-claim.close`, `kcom-claim.collect`, `kcom-claim.settle`, `kcom-claim.finish-settlement`, `kcom-claim.seal`, `kcom-claim.activate` and `kcom-claim.recover` operations use the campaign artifacts pinned from [contract PR #499](https://github.com/KASPACOM/kaspa-covenants/pull/499). Each builds an unsigned PSKT. The wallet signs the native fee input: index 2 for vault funding, opening, shard collection, per-claim settlement and sealing, index 1 for factory, selection, shard close and settlement-finish steps, index 2 for surplus recovery, and index 3 for activation. Opening, shard close and surplus recovery also need two distinct frozen administrator signatures on covenant input 0. Selection needs the original eligible native Schnorr authority signature on shard input 0. The graph-owned KCC20 reserve uses canonical owner-scheme-4 authorization by the vault input.

Funding requires two separate transactions. First, the existing canonical `kcc20.transfer` operation sends the exact campaign budget to the derived campaign graph covenant ID with owner scheme 4. After that accepted token output is live, `kcom-claim.fund-vault` spends it together with the still-unfunded vault output. The builder reconstructs the vault successor and unchanged canonical token reserve, checks both current source outpoints and their covenant IDs, and returns a rebuild-required error for stale sources. It pays the fee from a separate wallet UTXO. A submitted PSKT is not accepted funding until chain and indexer evidence confirm the spend.

The build request uses the existing `kcc20-in-process-pskt-builder-input/v1` envelope with `builderKey: "kcom-claim.fund-vault"`, `network: "testnet-10"`, a TN10 `owner.walletAddress`, and these `params`:

| Field | Meaning |
| --- | --- |
| `graphId` | Derived campaign graph covenant ID, 32-byte hex |
| `vaultState` | Exact current `KCOMVault` state, including frozen terms and `funded: false` |
| `vault` | Current vault `{ transactionId, index }` outpoint |
| `tokenState` | Exact graph-owned canonical KCC20 source state |
| `token` | Current token `{ transactionId, index }` outpoint |

To open, call `kcom-claim.open` with `params: { graphId, factoryState, vaultState, factory, vault, adminPublicKeys }`. The keys must be two distinct members of the three frozen administrators. This first build preserves both covenant outputs and returns `submitTransactionSupported: false` plus `metadata.adminSigning.signingCommitment`. Each administrator signs input 0 of the returned `psktTransactionJson` with SIGHASH_ALL using their own wallet. Call the same operation again with ordered `adminApprovals: [{ publicKey, signature }, ...]` and `expectedSigningCommitment`. It rechecks live sources and exact output/fee fields, rejects a changed signing intent, and returns the final PSKT for the separate fee wallet to sign input 2. The builder checks public-key membership and signature encoding; the covenant checks signature validity during execution. The backend must not mark opening accepted from the prepared or submitted PSKT alone.

After the campaign factory is opened, `kcom-claim.create-shard` spends its current factory outpoint and creates one numbered shard. Its request uses the same envelope with `builderKey: "kcom-claim.create-shard"` and `params: { graphId, factoryState, factory }`. `factoryState` is the exact open `KCOMFactory` state; `factory` is its current `{ transactionId, index }` outpoint. The builder derives the next factory state and initial shard state from that source, preserves their combined native KAS, and rejects a stale factory or a completed shard sequence. Each accepted shard creation consumes the previous factory, so the next build needs the new outpoint and incremented state. Once every shard exists, `kcom-claim.finish-initialization` takes the same request fields and replaces the final factory with the initial settlement collector. The collector inherits the factory's native KAS and starts with empty participation totals.

To select a tier, call `kcom-claim.select` with `params: { graphId, shardState, shard, eligibilityProof, authorityPublicKey, tier, beneficiary, unusedProof }`. The proof includes the original scheme-0 authority, base entitlement and canonical Merkle siblings. The builder authenticates the frozen eligibility root, unused slot, shard route, exact successor state and beneficiary-bound commitment. The first response is a prepare PSKT with `submitTransactionSupported: false`. The original eligible authority signs input 0 of that PSKT with SIGHASH_ALL. Rebuild with `authorityApproval: { publicKey, signature }` and `expectedSigningCommitment`; the builder rechecks the live shard source and protected outputs, then returns the PSKT for the separate fee sponsor to sign input 1. The sponsor funds one native-KAS commitment cell. Selection remains irreversible after acceptance. The current integrated contract authenticates original native Schnorr authorities only; production source manifests containing other authority schemes require a reviewed contract path before opening.

After the frozen close time, call `kcom-claim.close` once for each live shard with `params: { graphId, shardState, shard, adminPublicKeys }`. As with opening, its first response is a prepare PSKT with `submitTransactionSupported: false` and an administrator signing commitment. Two distinct frozen administrators sign input 0 from that exact PSKT. Rebuild with ordered `adminApprovals` and `expectedSigningCommitment`; the builder rechecks the current shard source and all protected outputs before returning the PSKT for the separate fee wallet to sign input 1. It commits `lockTime` to the frozen close time plus one millisecond. The covenant enforces the time and administrator threshold; a submitted transaction alone does not establish accepted closure.

After accepted manual close, `kcom-claim.collect` takes `params: { graphId, collectorState, closedShardState, depth, unusedProof, collector, closedShard }`. It verifies the next numbered closed shard, an empty summary slot and matching campaign terms, then replaces both inputs with one collector carrying their native KAS and combined participation. `unusedProof` is the hex Merkle proof for the empty summary slot, and `depth` must match the power-of-two shard count. For each accepted selection, `kcom-claim.settle` takes `params: { graphId, collectorState, commitmentState, closedShardSummary, collector, commitment, summaryProof, summaryDepth, usedProof, usedDepth }`. It verifies the closed shard summary against the collected root, the selected claim against that shard's final used root, the original authority identity, the frozen campaign and current source UTXOs. It computes the exact base, Medium, Long and unclaimed-Long shares with integer rounding, increments the collector liability and replaces the one-time commitment with an immutable entitlement carrying the same native KAS. The sponsor signs input 2. Each accepted settlement consumes the previous collector, so subsequent claims must rebuild from its new output.

After the collector has processed every shard and entitlement, `kcom-claim.finish-settlement` takes `params: { graphId, collectorState, collector }`. It requires complete shard coverage, exact settlement count and a liability within the budget. It preserves the collector's native KAS while marking the state complete. Then `kcom-claim.seal` takes `params: { graphId, vaultState, collectorState, vault, collector }`. It verifies that the funded vault remains unsettled and that the collector is complete. It spends both graph actors, preserves their combined native KAS in one settled vault output, and freezes the exact liability carried by the collector. The sponsor pays each fee. None of these steps consumes a token reserve.

After settlement, `kcom-claim.activate` takes `params: { graphId, vaultState, entitlementState, tokenState, vault, entitlement, token }`. States must match their live source UTXOs and the frozen campaign identity. The operation spends the vault, one immutable entitlement and its exact canonical token reserve, derives a new beneficiary-bound vesting position from vault input 0 and position output 1, and transfers the **full** entitlement into that position's reserve. It automatically chooses partial activation when a vault reserve remains and final activation when this is the last liability. The sponsor pays the fee and any native KAS needed to split the token reserve. Activation pays no TGE tokens; the separate vesting release operation handles that. A stale or competing source requires rebuilding with the new accepted outpoints.

After sealing, `kcom-claim.recover` takes `params: { graphId, vaultState, tokenState, vault, token, adminPublicKeys }`. The frozen liability determines whether recovery is partial or final. Partial recovery sends exactly `budget - liability` tokens to the frozen treasury and leaves `liability - activated` in the graph-owned reserve; final recovery sends the entire remaining surplus when no beneficiary liability remains. Both paths keep the vault native KAS and mark it recovered exactly once. The first response is a prepare PSKT with `submitTransactionSupported: false`. Two distinct frozen administrators sign vault input 0 with SIGHASH_ALL; rebuild with ordered `adminApprovals` and `expectedSigningCommitment`, then the separate fee sponsor signs input 2. The builder verifies the current vault and canonical token UTXOs, token amounts, extension, treasury identity, output scripts, token KAS and sponsor change. An accepted recovery never spends an unactivated beneficiary allocation.

The local pinned-WASM test checks artifact pins, source and successor scripts, amounts, signing indexes, stale-source rejection and fee-output mutation. Vault funding's scripts, all four shard-creation successor scripts, the initial collector and sealed vault scripts, and the first partial/final activation scripts and position IDs match the synthetic Argent-engine `tn10-proof-mixed` receipt in [#499](https://github.com/KASPACOM/kaspa-covenants/pull/499). The builder commits budgets 60/20 for vault/token inputs, above measured 52/15; 70/15 for opening, above measured 47/5; 40 for selection, above measured 25; 50 for shard close; 30 for shard creation, above measured 22; 40 for initialization finish, above measured 29; 45/30 for collection, above measured 31/23; 40/30 for per-claim settlement, above measured 23/20; 40/25 for sealing, above measured 28/15; 120/35 for recovery vault/token inputs, above measured 95/25; and 100/35 or 70/25 for activation vault/token inputs, above measured 79/25 or 56/15. Fee inputs commit 10. Local signed wire tests in #499 execute the available campaign PSKTs in Argent against synthetic sources; none establishes TN10 acceptance. Backend accepted-deployment verification, token-profile transfer compatibility and funded multi-wallet proof remain required before using real campaign funds. Campaign initializer deployment and the linked two-administrator graph creation have passed the local pinned Argent engine, but no funded TN10 campaign creation has been submitted. Other original eligible authority schemes remain unsupported by the integrated selection contract.
